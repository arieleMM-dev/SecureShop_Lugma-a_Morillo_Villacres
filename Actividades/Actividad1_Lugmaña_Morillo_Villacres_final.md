1. # **Actividad 1: activos de Secure Shop**

| Activo | Tipo | Consecuencia de acceso no autorizado,modificado o indisponible | Amenazas | Control |
| ----- | ----- | ----- | ----- | ----- |
| Información personal y de contacto de los usuarios | Información | En caso de que la información haya sido modificada los perfiles podrían contener direcciones o contactos erróneos, lo que afectaría la atención y la entrega de pedidos. | \-Un atacante explota una vulnerabilidad en las APIs para extraer la base de datos de clientes, vulnerando la Confidencialidad y afectando la confianza en secure shop. \-Un fallo crítico en el base de datos exclusivo de este dominio borra los registros, bloqueando por completo la disponibilidad para el inicio de sesión. \-Un fallo en la lógica del microservicio sobrescribe o mezcla información de contacto entre distintos usuarios, afectando la Integridad. | Implementar validación estricta de esquemas en las entradas del API (ej. DTOs validados) y transacciones atómicas con bloqueo optimista en la capa de persistencia. |
| Credenciales de acceso y sus representaciones protegidas | Información | En caso de que  que tener un acceso no autorizado un atacante podría intentar tomar cuentas o reutilizar credenciales expuestas en otros sistemas, para afectar la integridad de los mismos  | \-Atacantes automatizan peticiones masivas usando credenciales robadas de otros sitios para intentar entrar al sistema. \-Intercepción o falsificación de tokens de autenticación.  \-Descifrado de hashes por algoritmos obsoletos. | Implementar limitación de tasa (Rate Limiting) y mecanismos de protección contra bots (como CAPTCHA) en la pasarela o punto de entrada común (API Gateway). |
| Catálogo de productos, descripciones y precios | Datos | En caso de que este activo sea modificado se mostrarían productos, descripciones o precios falsos; los clientes podrían realizar pedidos con información incorrecta. | \-Un actor malintencionado vulnera los permisos del servicio de productos y altera los precios a valores mínimos (ej \$0.01), generando pérdidas económicas masivas antes de ser detectado. \-Saturación de peticiones al microservicio de productos desde el punto de entrada, impidiendo que los clientes potenciales visualicen el stock y las ofertas de secure shop. \-Robo de información de la Empresa extraccion de todo el catálogo, descripciones técnicas y estrategias comerciales de secure shop por parte de la competencia. | Exigir autenticación y autorización basada en roles |
| Registros de pedidos y su estado | Datos | En caso de que el activo no este disponible  Los clientes y el personal no podrían consultar ni procesar pedidos. | \-Alteración de estados de pago o envío , un atacante logra inyectar o modificar registros directamente en la base de datos de pedidos. \-Interrupción en el flujo de pedidos caída o latencia límites  en el microservicio de pedidos o en su comunicación con el de productos impide registrar nuevas compras. \-Exposición de los registros de transacciones debido a un control de acceso defectuoso en las APIs de consulta | Aplicar controles de autorización a nivel de objeto, garantizando que el microservicio de pedidos verifique que el usuario autenticado solo pueda consultar sus propias transacciones. |
| Servicio de usuarios | Servicio | En el caso de que el activo no este disponible el registro, la autenticación o la gestión de perfiles dejarían de funcionar. | \-Saturación de solicitudes de registro e inicio de servicio dirigidas al microservicio de usuarios, bloqueando la entrada tanto a nuevos clientes como a compradores frecuentes \-Explotación de parámetros mal validados en los endpoints de gestión de usuarios para ejecutar comandos arbitrarios en la base de datos de este dominio \-Uso de librerías desactualizadas en el stack tecnológico del microservicio que permitan ejecución remota de código   | Desplegar servicios de mitigación de DDoS en la capa de borde y configurar cuotas estrictas de recursos (*resource quotas*) en los contenedores del clúster de microservicios. |
| Código fuente de los microservicios y del punto de entrada | Software | Se podrían descubrir detalles de implementación que ayuden a buscar fallas; cualquier secreto incluido por error también quedaría expuesto. Podría incorporarse código malicioso o defectuoso que afecte a los despliegues posteriores. El equipo no podría revisar, corregir ni desplegar nuevas versiones desde el repositorio. | \-Filtración de claves, tokens, contraseñas, subidos por error al repositorio. \-Inyección de código malicioso por una cuenta comprometida o un colaborador no autorizado. \-Eliminación o corrupción del repositorio (por error humano o sabotaje). | Proteger las ramas principales con revisión obligatoria de pull request y autenticación multifactor. |
| Base de datos de usuários | Infraestructura | Se podría acceder directamente a la información de cuentas almacenada. Se podrían alterar o borrar registros de usuarios, afectando la identidad y la integridad de las cuentas. El servicio de usuarios no podría recuperar ni guardar cuentas. | \-Inyección SQL (o NoSQL) que permita leer o modificar cuentas. \-Acceso directo a la base por credenciales débiles o expuestas. \-Robo de datos personales o contraseñas por una filtración.  | Almacenar las contraseñas con *hash* y *salt* (bcrypt o Argon2), usar consultas parametrizadas y restringir el acceso a la base solo al servicio de usuarios.  |
| Base de datos de productos | Infraestructura | Se podría consultar directamente información del catálogo almacenada, incluso la no expuesta al público. Se podrían alterar o borrar productos y precios sin pasar por las reglas del servicio. El servicio de productos no podría consultar ni actualizar el catálogo. | \-Alteración no autorizada de precios o productos sin pasar por las reglas del servicio. \-Borrado masivo de datos por error o ataque. \-Exposición de información del catálogo no pública (productos no lanzados, costos).  | Aplicar el principio de mínimo privilegio con cuentas de base de datos separadas por servicio (solo lectura donde corresponda) y respaldos periódicos.  |
| Base de datos de pedidos | Infraestructura | En caso de modificación se podrían alterar o borrar pedidos y estados, perdiendo la trazabilidad de las operaciones. El servicio de pedidos no podría registrar ni recuperar pedidos. | \-Modificación de pedidos o estados para fraude o pérdida de trazabilidad. \-Denegación de servicio que impida registrar o consultar pedidos. \-Acceso no autorizado a datos de compradores (direcciones, historial).  | Registrar auditoría de cambios (quién, cuándo y qué modificó) y cifrar los datos sensibles en reposo y en tránsito.  |
| Configuración de despliegue y comunicación entre servicios | Información | En caso de un acceso no autorizado, se revelarían direcciones internas, parámetros de conexión o secretos si estuvieran guardados allí.  En caso de indisponibilidad, si la configuración necesaria no estuviera disponible, los servicios podrían fallar al iniciar o comunicarse. | \-Exposición de direcciones internas y secretos guardados en archivos de configuración. \-Suplantación de un servicio o interceptación del tráfico entre microservicios. \-Modificación maliciosa de la configuración que cause fallos al desplegar o iniciar.  | Gestionar los secretos con un gestor dedicado (variables de entorno seguras, Vault o secretos de Docker/Kubernetes) y usar TLS entre servicios con autenticación mutua.  |
| Entorno de ejecución de los microservicios (contenedores o máquinas virtuales) | Infraestructura | Acceso: acceso al entorno podría permitir inspeccionar procesos o alcanzar otros componentes. Modificación: ejecución de imágenes maliciosas o debilitamiento del aislamiento. Indisponibilidad: los servicios alojados dejarían de responder. | \-Explotación de vulnerabilidades en imágenes o componentes desactualizados. \-Escape del contenedor por configuración privilegiada o aislamiento débil.- Agotamiento de CPU, memoria o conexiones que provoquen denegación de servicio. | Usar imágenes confiables y analizarlas antes del despliegue; ejecutar contenedores sin privilegios y aislados; aplicar parches y límites de recursos. |
| Copias de respaldo de las bases de datos | Datos | Acceso: exposición de información personal, productos o pedidos contenidos en las copias. Modificación: copias alteradas que impidan una restauración íntegra. Indisponibilidad: no se podrían recuperar los datos tras una pérdida o incidente. | \-Robo de copias por permisos de almacenamiento demasiado amplios.- Borrado o cifrado por ransomware con acceso a la cuenta de respaldo. \-Corrupción silenciosa o fallo de restauración por copias incompletas o no probadas. | Cifrar las copias; restringir su acceso y mantener una copia inmutable o desconectada; probar periódicamente la restauración. |
| Credenciales de comunicación entre microservicios | Información | Acceso: quien las obtenga podría hacerse pasar por un servicio. Modificación: sustitución de credenciales que redirija o interrumpa la comunicación. Indisponibilidad: los servicios no podrían autenticarse entre sí. | \-Filtración de tokens en código, variables de entorno, registros o repositorios. \-Reutilización o reproducción de un token robado para suplantar un servicio. \-Movimiento lateral entre servicios debido a credenciales con permisos excesivos. | Guardar credenciales en un gestor de secretos; rotarlas y preferir credenciales de corta duración; asignar identidad y permisos mínimos a cada servicio. |
| Registros de actividad y eventos de seguridad | Datos | Acceso y tener tendencia a exposición de detalles operativos o datos sensibles registrados. Modificación,eliminación o alteración de evidencias que dificulte detectar incidentes. Indisponibilidad: se perdería visibilidad para alertar e investigar. | \-Borrado o alteración de registros para ocultar actividad maliciosa. \-Inyección de entradas falsas mediante datos no validados. \-Saturación del almacenamiento con eventos repetidos, impidiendo registrar actividad útil. | Centralizar los registros en almacenamiento de solo anexado; restringir el acceso y alertar sobre cambios o saturación; filtrar datos sensibles y entradas no confiables. |
| Certificados TLS y sus claves privadas | Información | Acceso para realizar robo de una clave privada que permita suplantar el sitio o servicio. Modificación de claves o parámetros que debilite la protección de las conexiones. Indisponibilidad al tener certificados vencidos o inválidos provocarían errores de conexión. | \-Robo de la clave privada y suplantación del servicio. \-Vencimiento o renovación fallida que interrumpa las conexiones seguras. \-Configuración criptográfica débil que facilite interceptar comunicaciones. | Proteger las claves en un gestor seguro con acceso restringido; automatizar y supervisar la renovación de certificados; configurar protocolos y algoritmos seguros. |
